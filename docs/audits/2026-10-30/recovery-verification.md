# A1 / A2 复现与修复记录

对应 [架构诊断](architecture-and-ui.md) 的 A1、A2。按用户后续指令修复，沿用 `feat/review-workbench`；无前端样式变更、无新增依赖。

## 复现证据

先新增 `tests/test_recovery.py`，在改动运行代码前执行：

```powershell
python -m unittest tests.test_recovery -q
```

旧实现：`Ran 3 tests in 14.457s`，`FAILED (failures=9)`。具体失败包括：

- 提交和导入写出历史后强制退出，重新打开仍见旧 revision。
- 提交、导入或解决冲突写完草稿后退出，comparison 中的冲突状态未跟随更新。
- 同一个 Store 经历写入异常后，旧 revision 仍被接受，能够再次产生提交。
- compare 的 Git diff 计算期间实际插入新的相反决定，旧 compare 没有返回 409，继续覆盖新冲突视图。

故障注入在真实 atomic_json 完成后调用子进程 `os._exit(73)`，不用异常清理模拟进程退出；父进程确认退出码，再通过新 Store 读取实际磁盘结果。比较竞态通过在 Git diff 调用处精确插入真实提交控制顺序，不依赖 sleep 或随机线程调度。

## 修复

`Store._commit` 在持有共享包锁时，先原子写入本次操作的完整意图，包括目标草稿、新增不可变提交及比较结果。日志落盘后，操作进入必须完成的状态。恢复顺序是校验材料与记录身份、检查已有提交不冲突、补齐提交、替换草稿、替换比较、移除意图文件。

每次进入 Store.lock 都先恢复，不仅在构造 Store 时恢复。因此原服务中的写入错误也不会留下一个允许旧 revision 继续写的窗口。重复执行恢复使用相同的 submission_id 和目标 revision，不生成新提交、不再次递增 revision。导入在开始写入前计算包含所有新记录的完整投影，避免只恢复到部分导入。

compare 在锁内获取 revision 与历史快照，计算时释放锁；发布前再次持锁校验 revision 与历史指纹。不一致则返回 409，保留磁盘最新比较视图；用户或调用方重新运行后使用最新快照计算。

## 新增回归覆盖

6 个测试方法包含多种子场景：

- 提交、解决、导入分别在写提交、写草稿、写比较之后强制退出；导入另外覆盖多个提交中的第一个和第二个写入点。
- 同一 Store 的 I/O 异常后恢复并拒绝过时重试。
- 意图尚未落盘即失败时，操作没有产生历史、revision 或比较变更。
- 意图刚落盘即退出，随后恢复再被强制中断两次，最后仍完成唯一一次操作。
- 导入恢复后再次导入，同编号记录正确去重，草稿及 revision 不重复推进。
- compare 与新提交、导入、冲突解决、草稿保存交错时均返回 409，保留最新视图；重新执行 compare 成功。

## 保证范围

这次覆盖进程中断和写入异常，不声称证明断电、磁盘介质损坏或所有文件系统的掉电顺序。未完成意图必须保留；持久 I/O 故障仍会向调用方返回错误，修复磁盘问题后可继续恢复。

已经在旧版本中发生、且没有操作日志的半完成写入，无法可靠推断当时用户的完整操作意图；本次不会猜测并改写这些历史。新的日志只保证使用修复后代码开始的操作。导出时在包锁内先恢复，迁移包只携带完成后的状态。
