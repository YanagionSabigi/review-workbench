# 通用校对工作台设计

状态：用户已批准并授权实施。初稿日期：2026-10-29。

## 意图与边界

提供一个可由其他 skill 调用的人工审核环节：调用方准备材料与 AI 建议，用户在本地网页查看、选择、编辑或批注，结果保存为 JSON；用户回到聊天指示业务 agent 读取结果、修改原稿和继续工作。

美观、阅读舒适和减少无效文字是首要验收条件。主要处理大量零碎材料，包括术语、译文修改、报告修改、OCR 疑点、公式和图表。第一轮就可以对照两个 AI 工作版本，无须等到人工意见产生后才有 diff。

工具只处理通用材料、审核决定、展示、保存和打包。业务 skill 自己负责适配、生成建议、读取反馈、修改 EPUB/译文缓存/文章等业务原稿。本项目不包含 AiNiee、微信读书、PDF 转 EPUB 的专用适配器，不采集账号或调用模型。既有技能仅为需求调查参考。

不做云服务、账号系统、多人实时协作、数据库、业务原稿自动写回或按时间戳推断冲突。图片圈画先完成数据与交互设计，首版不实现绘图编辑器。原型为可丢弃草图，不直接充当正式代码。

## 已选路线与替代方案

用户选择 A：原生 HTML/CSS/JavaScript 模板 + Python 轻量本机服务。前端不需要 npm 构建；运行者需要 Python 和 Git。最终审阅确认仅浏览器校验会漏掉无效公式，因此按用户已允许 Python/Node 的环境要求，公式决定提交与导入另外用本机 Node 调用同份 KaTeX；普通文本不需要 Node。前端必要的公式渲染库及字体资源随包携带，正式包运行时不依赖 CDN。Python 版本、具体公式渲染库等为实施选择，见下文。

考虑过的 B：组件框架前端 + Node 服务，适合更大型应用，但增加构建与依赖管理，未采用。纯双击静态 HTML 无法可靠自动落盘，不作为主运行方式。

本工具项目已在本机 git init，不创建 GitHub 或其他远程仓库。设计、源代码、Schema 和示例由 Git 管理，预览服务状态及真实审核材料不提交到工具仓库。

## 使用闭环

1. 业务 skill 确定业务项目根目录、本轮文件范围，检查是否已有 Git（包括上层仓库和 worktree）；有则复用，无则初始化明确指定的项目根目录。
2. 调用方生成审核输入与所有资源。工具验证结构、引用及材料完整性，在本轮相关文件范围内建立 Git 基准。内容必须与基准提交一致，不能把旧 HEAD 错当作包含未提交修改的审核版本。
3. 启动本地服务，打开页面。所有人工输入自动保存到包内草稿 JSON；页面只有收到后端落盘确认才显示保存成功。
4. 用户可以逐项、整页或多选审核，也可以只提交已完成的一部分。保存草稿与提交本轮是两个动作。
5. 提交创建不可变的决定文件并关联材料基准 Git 提交。后续更改形成新提交记录，不覆盖已提交的决定。
6. 用户回到聊天指示业务 agent 读取已提交决定。业务 agent 应用决定，处理意见或提供新建议，向工具提供更新后的通用材料。工具服务不直接编辑业务原稿。
7. 如需验收或存在冲突，再次展示版本差异及人工决定。用户也可改选以往决定，历史仍保留。

用户允许业务 agent 在人工回复前先应用 AI 推荐。自动应用不等于人工审核，不使任何审核项自动变绿；红色项尤其不能冒充已由人批准。

## 页面与视觉约束

默认 A 单项专注：左侧主目录与少量交叉筛选，中间审核项列表，右侧当前项。保留 B 连续阅读视图作为可选，切换入口轻量，不用遮挡正文和操作的悬浮演示条。

顶栏只保留必要身份与提交入口。列表项保留编号、必要状态和具体定位标题；正文以实际材料为主，不重复列表标题、摘要或泛化建议。删除旧草图中的标语、日期、演示横幅、功能解释、目录解释、条目重复摘要、“− 删除/＋ 添加”图例、“可划选上方文字并引用”等文字。原型限制在聊天和文档中说明，不把技术说明长期塞进产品页面。

“修改依据”是业务材料的一部分，可以简短显示；长依据与来源上下文可展开。空内容不占位。错误、未保存和冲突必须有简短可操作的提示，不能为了简洁隐去真实问题。

色彩克制：浅暖中性背景、清晰中文排版、局部红绿 diff。绿色表示已有人类有效决定；蓝色表示待审且有推荐；红色表示必须人工判断。文字/图标和可访问名称共同表达状态，不只靠颜色。选择按钮是用户明确要求的互斥状态控件，选中填色并非预先把某个方案设为主操作。

字体、间距、圆角、颜色使用统一 token。正文优先 18px、适当行高，界面文字 14px；具体值在新版草图中校验。中文双栏不机械套用英文字符数：以实际中文行长、阅读节奏和用户反馈为准。图片保持比例、不裁切关键内容，不按普通头像式 object-cover 处理证据图。

依 Refactoring UI 顺序审阅：层级 → 布局与留白 → 排版 → 颜色与对比度 → 深度 → 图片 → 交互收尾。桌面及 375px 窄屏实际渲染检查；窄屏需可打开目录筛选，而非简单永久隐藏功能。默认浅色，暗色首版不做，作为实施者提议而非用户要求。

## 四选一决定与状态

四个按钮初始都为透明底黑字：接受建议、保留原版、手动修改、提出修改意见。互斥选择；仅当前选择纯色底白字，并通过 aria-pressed 或等效语义表达。右侧不再重复显示决定文案。

| 选择 | 展开内容 | 有效条件 | 提交结果 |
| --- | --- | --- | --- |
| 接受建议 accept | 无输入框 | 有完整可接受的建议 | 精确绑定本轮建议，不能解析成未来最新建议 |
| 保留原版 keep | 无输入框 | 有原版 | 精确绑定本轮原版 |
| 手动修改 edit | 编辑区，预填建议；无建议时预填原版 | 至少一个可编辑块，用户已实际编辑，所需内容非空且格式合法 | 各块完整最终文本，不只保存可视 diff |
| 提出修改意见 comment | 意见框和引用 | 有非空的人工意见；仅引用不算意见 | 原文引用及意见交给 agent，非自动应用的最终稿 |

输入与选择自动保存，切换模式保留各自草稿，只有当前模式参与提交。选择手动修改或意见后，内容未满足条件仍不计已审；清空内容会失去有效状态。公式无法渲染时保留代码及错误，不允许以渲染成功假象通过；comment 仍可用来说明错误。

审核状态（待审/必审/已审）与后续处理状态（待 agent 处理/已应用/待验收/冲突）是不同字段。comment 可以计入人已审，但必须继续保持需 agent 处理。绿色不代表整个业务任务已完成。

用户的当前项在保存或改选时不突然消失；目录计数可以更新，在离开当前项后才遵循“只看未审”过滤。最后一项完成后有简短的完成/返回入口。

## 分类、筛选与批量操作

每项有唯一 item_id 和唯一主目录 group_id。主目录由调用方按任务提供，不能把业务分类写死在模板里。一条问题只列一次；同一目标上的不同审核意见可以是不同 item_id，须通过通用 target_id 建立关联，以发现互相不兼容的决定。

交叉维度由调用方提供，默认仅显示少量有意义的选项。例如含图像、含公式、语言风格、领域；选项可交叉，同一项各入口共享决定。首版确定性语义为选中的条件取交集，状态与主目录继续叠加；这是实施者选择。待审过滤涵盖普通待审与必审，另有只看必审入口，避免漏掉红色项。

整页/多选批准只接受有效推荐，跳过红色项、已有决定项、已有人工草稿项、无推荐项和冲突项。先显示范围、符合条件数量和跳过数量，再由用户确认。筛选后的“整页”明确指当前可见结果页，不包括其他筛选或未加载页面。多页数据按明确分页处理，不能把整个结果集伪装成一页。

## 文本、图片、公式与表格

通用内容块包括 text、tex、image、table。条目可以同时包含多种块，源材料与建议按 block_id 配对，不按数组位置猜测。

文本按词/字符显示 diff，中文不能依赖空格分词。删除使用红色与删除线，添加使用绿色与轻量下划线；窄屏可上下对照。无差异不强造 diff。业务模型的输出一律视为内容，HTML 转义；首版不执行调用方提供的 HTML、JavaScript 或公式中的外链命令。

文本划选后出现“引用”操作，进入 comment 模式。引用独立于意见正文保存，包含 item_id、block_id、所选版本、基准 Git 提交、精确文字、前后文及文字范围。重复片段靠范围和上下文定位；后续文本改变时不静默重新绑定。跨版本/跨块选择首版不支持，提示分开引用，属实施者选择。

图片提供局部与整页资源（由调用方准备）、适应窗口/原始比例、缩放和平移。资源记录 source_id、物理页、可选印刷页、图像尺寸与可选区域坐标。图片批注预留归一化坐标、形状类型、关联意见、对应资源版本；首版仅设计 Schema，不提供不可用的圈画按钮。

公式源图与渲染结果对照，TeX 可在 edit 模式直接修改并本地渲染；代码仍可查看。正式版包含离线数学渲染库，具体选型在实施时按公式覆盖和资源体积核实。不承诺任意 LaTeX 文档编译；未知宏/不支持语法清晰报错，并可由调用方提供预渲染图作为证据，不能默默丢掉命令。

表格以单元格数据展示和编辑，保留行列结构；图表为源图与提取的文本/表格/说明对照，不做图形重绘工具。富媒体内容只能引用包内资源，外部来源地址作为可点击出处而非运行时依赖。

## 数据与 Schema

正式实施时提供 JSON Schema Draft 2020-12 和可通过验证的示例。逻辑分为三类文件，而非一个混合可变文件：

- package.json：schema_version、package_id、title、基准 Git 引用、主目录、筛选维度、items、资源清单。每项包含 item_id、target_id、group_id、facet_values、requires_human、before/baseline/proposal 的块、evidence、依据和来源。所有源文件路径均由显式范围清单限定。
- drafts.json：package_id、材料 Git 基准、单调递增 revision、各项选择、各模式草稿及引用。revision 用于防止两页同时保存互相覆盖，不以时间顺序判业务冲突。
- submissions/SUBMISSION_ID.json：不可变的本次提交范围、材料基准、完整决定及引用。只输出当前有效模式，保留与历史提交的关联。submission_id 为随机标识，不以时间戳作为版本机制。

JSON Schema 校验字段与类型；跨引用、资源实际存在、item/block/target 关系、必需内容、推荐是否存在等业务约束由 Python 同时验证。Python 使用一个明确声明的小型 Schema 验证依赖是允许的实施选择，服务框架与数据库不引入；不能用“不引入依赖”替代实际验证。所有运行依赖通过单一 requirements 文件说明并支持随包带离线 wheel 的导出选项。

版本名称明确分开：before 是页面左侧“原版”，keep 精确选择它；proposal 是页面右侧建议，accept 精确选择它；baseline 是准备本轮时业务工作稿的实际状态，被 Git 基准固定；evidence 是外文、扫描图等证据，不会被 keep 当成目标稿。一般 before 与 baseline 相同。若业务 agent 已先应用建议，baseline 可能等于 proposal，但 before 仍是本轮需要展示的修改前版本。人工决定回传时，三方比较使用 baseline、此时的工作稿投影与人工所选最终内容；不能因为选项叫“保留原版”，就把 before 错用为 Git 三方基准。这一命名澄清来自独立设计审阅，不新增业务行为。

材料多块时决定保存对应 block_id 的完整 edits。image 块本身不允许文本编辑；只含图像而没有可编辑结果的条目，不显示可用的“手动修改”，可提出意见；四按钮布局保持，禁用并用可访问名称说明原因。数据不能凭空声称某个完整人工决定或真实修改已执行。

包中必审但没有方案的条目保持红色；建议为空时接受按钮不可用。渲染、保存、打包失败不能标成成功。

## 本地服务与保存

使用 Python 标准库 HTTP 服务和模块化前端，无数据库。浏览器只访问当前审核包及静态前端资源，服务仅监听 127.0.0.1 随机可用端口。启动会自动打开页面并打印完整本地 URL。

建议命令（名称可在实施中调整但必须一致）：

```text
python -m review_workbench prepare --project PROJECT --input INPUT --scope SCOPE
python -m review_workbench serve PACKAGE
python -m review_workbench export PACKAGE --out ZIP
python -m review_workbench import-results PACKAGE --from RETURNED_PACKAGE
python -m review_workbench compare PACKAGE --current CURRENT_JSON
```

prepare 在业务 skill 授权的明确项目/文件范围内生成材料并准备基准；serve 的职责仅是当前包的读写与展示，不越过协议改写业务文件。

API 提供读取材料与草稿、带 expected_revision 的草稿保存、指定 item_id 范围提交、提交历史、结果导入与比较。自动保存采用短防抖、串行写入和递增 revision；冲突返回 409 并保留本地输入，用户可选择恢复/比较，不能靠最后写入覆盖。临时文件与目标同目录，先完整写入再原子替换；提交、导入与写回有包级锁。

保存中的状态可用小图标表达；失败必须给出简短文字与重试入口。离页前有未落盘改动时提醒，不能假定关闭浏览器事件一定可以保存。后端退出后页面明确失联，不把浏览器内存当持久化。写 API 限制同源与启动令牌；资源路径限制在包根，拒绝穿越、符号链接逃逸及 ZIP 路径逃逸。导入的审核包不能触发任意命令或自动执行随包脚本。

## Git 基准与冲突

Git 是材料版本依据，不再另设基于时间戳的业务版本系统。用户同意对本轮相关文件作范围限定的基准提交。不能提交无关已暂存文件；不能默认 stash、清空暂存区、切换分支或 reset。Git 仓库尚无首个提交也必须正常建立初始基准。被忽略的文件、子模块、跨仓库或不在指定项目范围的文件，准备阶段明确指出，由调用方先整理为可审核材料，不擅自强制加入。

工作区干净且内容已在 HEAD 中时可以复用该提交；存在本轮相关修改时只提交明确范围。用户身份未配置等失败保持文件原样，提供修复信息，不修改全局 Git 配置。基准引用不得只记录可移动分支名，必须记录 commit ID。

compare 接受业务 agent 提供的 CURRENT_JSON，作为当前工作稿的通用投影；工具无需知道原稿业务格式。比较先校验 package/target/block 身份，再把内容映射成稳定的、按 target/block 分离的文本文件，使用 Git diff/三方比较能力，避免仅因整个 JSON 的字段变化报告全文件冲突。二进制与图像按版本及资源差异标记，不做文本合并。

三份内容分别为基准、当前工作稿和人工决定。当前稿与决定一致为已满足；当前稿仍等于基准为可交由业务 agent 应用；双方改变且结果不一致时列出冲突（首版保守，不自动合并不同位置的编辑）。comment 无最终文本，只形成待 agent 处理项。同一 target 上不同 item 决定相互矛盾，或不同提交对同一项作出不同决定，也列为冲突，显示来源与差异，不因较新提交而覆盖。

工具只输出 comparison/冲突结果，不自动 apply/merge 原稿。Git 无文本冲突也不等于语义通过；逻辑或术语层面的判断留给业务 agent 和人。

## 可迁移审核包

ZIP 包含材料、相对路径资源、静态前端、Python 启动入口、依赖说明、Schema、基准和人工结果。不能包含源机器绝对路径依赖、账号信息或整个业务仓库历史。

导出在独立暂存目录构造“只含本审核包材料”的最小 Git 仓库，作为可迁移版本依据，并记录原项目基准 commit ID 与原 package_id 的对应关系；不复制原业务 .git。此处新建的是导出包自己的仓库，不在业务源项目内创建嵌套仓库。这是对迁移边界的实施者选择。导出始终从已确认的材料基准产生，禁止把导出过程中的新建议静默混入旧审核包。

接收者解压、安装声明的轻量依赖并运行 Python 启动入口。静态资源和数学资源全部本地；网络断开也能审阅与保存。有必要时可只回传结果包，保留 package_id、item_id、原基准、决定与必要引用，不要求回传全部图片。

导入结果按身份与基准校验、去重。原业务仓库不需要直接合并朋友的 Git 分支；由原基准关联回材料，再用 Git 对照当前投影和决定。历史缺失、材料不匹配或有改选时列出问题，不自动覆盖。运行中的旧审核包材料是冻结的，新材料必须创建新基准/新轮次，防止人边读边变。

## 验收

- 用户截图中框出的文字消失；四选择初始无高亮、互斥高亮正确，输入区按模式展开。切换条目与视图不丢草稿，已审过滤不打断当前项。
- 真实中文 diff、直接编辑、划选引用、术语、多块内容、图片放大/平移、公式编辑/渲染失败、表格结构可验证；不以只读截图冒充联动功能。
- 保存到 JSON 后重启恢复；保存失败、并发保存、409、部分提交、重复提交、人工草稿切换均正确。
- 批准范围准确，红色项和人工草稿不能被批量盖过；comment 与业务完成分开。
- 新仓库、已有仓库、无关暂存修改、相关未提交修改和 worktree 均有验证；不污染无关文件与暂存内容。
- 相同结果、仅人工改变、仅工作稿改变、双方不同、同目标多决定、旧包回传、缺少基准与二进制变更均有可解释结果。
- ZIP 在新目录运行、离线资源可用、结果可回传；不携带原业务 Git 历史和绝对路径。路径穿越、恶意 HTML 和错误包被拒绝。
- 桌面与窄屏检查图片/公式可读性、对比度、键盘焦点、选中语义及空状态。

## 留给实施者的选择

在不增加用户工作负担前提下确定 Python 最低版本、数学渲染库、diff 算法、轻量 Schema 校验依赖版本、前端文件拆分、分页阈值和性能优化。必须通过官方资料核实所选依赖并记录许可证。桌面优先、浅色优先、首版单实例包级锁；大规模在线协作不在范围。以上实施者选择不应伪称用户已经逐项要求。
